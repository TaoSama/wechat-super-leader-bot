# 模型决策层与持久化对话

## 本次增量与不变架构

Controller 仍是唯一控制权威；独立微信 Gateway 只承载渠道。Go Daemon 原生附着宿主机已有会话，Controller/Web/PostgreSQL 在 Docker；不引入隔离 worker，不恢复历史会话冒充附着。

本次补齐每条自然语言消息触发的模型工具循环和按聊天隔离的持久化状态。用户选择模型 API 后，Leader 可主动查询多个节点/会话，再提出最多四个无相互依赖的任务；确认由 Controller 单独识别，模型工具里没有 confirm/send。技能目录及版本绑定委托参见 SKILLS.md。持续自治、依赖 DAG 调度及 Claude/Grok 适配仍待后续实现。

## 请求流程

1. HTTP 管理鉴权与微信 chatId 允许名单先于任何模型调用。
2. 按 chatId/messageId 查询已保存回执；相同 ID、不同文本拒绝。
3. PostgreSQL CAS 取得聊天处理权；同聊天并发消息不相互覆盖。
4. 非确认消息进入有限工具循环；节点和会话输出以 tool 消息传入，不提升为系统指令。模型只可读取证据、维护聊天记忆或提出待确认计划。
5. 计划保存到 leader_states 后才返回预览。确认消息原子消费计划，重新校验所有目标，然后走统一 CommandService，requestId 由计划 ID 与任务序号确定。
6. 命令持久化后、真实发送前再次检查处理权和期限。收到 accepted 只汇报输入已受理；没有终态则不宣称任务完成。
7. 最终回复、最近历史、记忆和回执通过 CAS 保存。进程在确认期间中断后，仅核查已有命令，不自动发送缺失项。

## 数据与模型边界

- Responses HTTP transport 仅向用户配置的服务商发请求；禁止凭证置于 URL、禁止重定向；连接/响应有超时与大小上限。使用 store:false，在同一工具循环中回传原生函数调用及 encrypted reasoning，不保留 Chat Completions 兼容层。
- 实例不读取用户其他应用的模型密钥，不选择或启用未经配置的服务商。
- 聊天历史、记忆按 chatId 隔离；工具查询命令仅允许当前聊天产生的命令 ID。
- 初版控制域为明确允许的操作者管理全部已注册节点；不是多租户 RBAC。若公司机器接入，需要先确认组织政策与可传送数据。
- 每轮和持久化数据都有大小上限。记忆不作为凭证保险库，常见凭证字段拒绝存储；不能因此声称具有全面 DLP。
- 模型文本本身不能证明完成，也不能替用户批准执行。真实模型规划质量需通过实际对话验收，本地脚本只能证明工具与状态机契约。

## 交付与验证门槛

- 新增 transport、持久状态 CAS、编排器单元测试；复跑原 Controller/Gateway/Web/Daemon 回归。
- 真实 PostgreSQL + 本地 HTTP 模型桩 + 模拟 Daemon 验证：先提计划不发送、重启保留计划、用户确认后单次发送、再次确认不重发、聊天记忆跨重启保留。
- 现有会话读取测试与真实发送测试分别记录。2026-10-11 用户授权新建专用测试会话并使用当前 Codex provider 的 gpt-6.1-sol；已通过真实模型工具调用、真实会话发送和模拟微信全链路。真实微信收发仍待用户人工验收。

## 运维

`LEADER_MODE=rules` 保留受限的规则入口；`LEADER_MODE=model` 必须同时配置模型 base URL、name 和 API key，缺项启动失败。模型错误不自动降级成执行规则。

此版本仅支持单 Controller 控制权威。状态 CAS 防止同聊天并发覆盖，不代表集群多活、跨进程执行 exactly-once 或容灾体系已经完成。
