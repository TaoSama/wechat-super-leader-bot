# 微信消息额度：按用户经历解释

固定规则：微信账号共享 **10 次发送额度**，窗口 **23 小时**；进入最后 1 小时（第 **22 小时**起），有任务或待发内容且只剩 **1、2 次**时提醒。提醒也消耗一次。这个规则没有改成 24 小时。

## 你会看到什么

| 场景 | 你做什么 | 系统做什么 |
| --- | --- | --- |
| 新开一轮 | 上午 8 点发一条真实新消息 | 这个收件人的回复窗口开到次日 7 点；账号共享额度刷新为 10 次。系统的普通回复也扣一次，所以回复后通常剩 9 次。 |
| 切换任务或业务会话 | 在同一微信聊天里换任务、查另一个会话 | 继续使用同一个 token 和账号额度，不会因换任务重新获得 10 条。 |
| 自动执行定时任务 | 到了计划时间，你没有发消息 | 任务照常执行并保存成果。窗口有效、额度足够时主动推送；否则保存等待，不靠你发消息才开始执行。 |
| 长结果或附件 | 一个结果分成 3 条，或摘要加一个文件 | 分别扣 3 次、2 次。图片、文件、进度和提醒都经过同一个账本。进度会给最终回复保留额度。 |
| 到第 22 小时，剩 1、2 次 | 不需要你先说话 | 有运行中任务、未来计划、待发成果或可恢复回复时，系统主动提醒你发一条消息。提醒优先，可用最后一次额度；同一账号窗口只提醒一次。 |
| 到第 22 小时，剩至少 3 次 | 继续等待任务 | 按当前已确认的低额规则不提醒，成果正常使用额度。若分段发送把剩余从 3 降到 2，下一段先给提醒让路。 |
| 额度已经用完，或超过 23 小时 | 你没有再发消息 | 系统无法再通过这条微信通道提醒或推送。成果持久排队；重启也不会自己补额度。 |
| 凌晨 4 点发一条消息 | 主动开启下一轮 | 刷新共享额度，优先回复当前消息，再恢复之前排队的成果；只续发未确认部分，不重跑任务。成果此时立即到达属于恢复投递。之前为什么没提醒，须核对当时的窗口、有效余量和任务兴趣，不能单凭恢复时间认定。 |
| 程序重启或网络回执丢失 | 不需要特殊操作 | 已确认分段不会重复；不知道微信是否收到了的发送保留为结果未知，不盲目补发。 |

## 多个实际收件人的情况

账号额度共享，发送凭证仍要对应实际收件人。官方参考实现按 `accountId:userId` 保存 `context_token`，不能把 A 的 token 发给 B（[官方入站实现](https://github.com/Tencent/openclaw-weixin/blob/main/src/messaging/inbound.ts)）。账号共享 10 次是本项目采用的额度策略。

- A、B 的业务任务合计消耗同一份 10 次额度，不各得 10 次。
- B 的有效新消息刷新账号额度后，A 若自己的 token 仍在 23 小时内，其排队成果也会恢复。
- A 自己的 token 已过期时，B 发消息不能续活 A；A 需要自己发一条新消息。
- A 的 token 已到第 22 小时，即使 B 刚刷新账号窗口，只剩 1、2 次且 A 有任务时，仍会在 A 的窗口结束前提醒。
- 跨收件人迟到的真实新消息可以更新自己的 token/窗口、恢复自己的成果；比账号最近入站更旧时，不重复补充账号额度。重放、无效时间和没有新 token 的消息不补额度。
- 当前有可发送的用户回复等待时，其他收件人的任务成果也让出共享额度；过期收件人的回复不会挡住所有人。

## 升级时会留下什么

原 token、收件人窗口、发送确认和排队成果保留。旧版本按聊天记额度，没有逐次发送时间；升级会保守汇总重叠窗口的已知消耗，可能暂时少给几次，但不会把多份余额相加。下一条有效的新入站恢复正常共享 10 次。生产只运行一个 Gateway，使用同一持久状态文件。

遗留 worktree 的功能与代码清单见 [审计报告](legacy-worktree-audit-2026-10-31.md)；这些旧修复没有整包混进本次额度修复。
